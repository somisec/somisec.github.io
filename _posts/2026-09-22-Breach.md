Breach is a medium difficulty Windows machine, where guest access to an SMB share is available. By leveraging write permissions on that SMB share, NTLMv2 hashes of a domain user are captured to obtain valid credentials. With access as a low-privileged domain user, a kerberoastable service account (svc_mssql) is revealed. After getting access to the service account, a Silver Ticket attack is performed to impersonate the Administrator user and gain access to Microsoft SQL Server. Through the xp_cmdshell feature, remote code execution is achieved as the svc_mssql service account. Finally, privilege escalation is performed by abusing the SeImpersonatePrivilege privilege.

This box is from Vulnlab but played on Hackthebox.

The User flag for this Box is located in a non-standard directory, C:\share\transfer.

#### Silver ticket
 
A silver ticket is a forged Kerberos service ticket (TGS), created using the NTLM hash of a service account. Unlike a golden ticket — which forges a TGT using the `krbtgt` hash and grants domain-wide access — a silver ticket only forges access to a specific service on a specific host.
 
In this machine the NTLM hash (derived from the recovered plaintext password) for the `svc_mssql` service account was obtained. This allows forging a TGS ticket for the MSSQL service, enabling authentication to the SQL Server as any user of choice, without needing that user's actual credentials.
 
##### Requirements
 
To forge a silver ticket, two pieces of information are required:
 
NTLM hash of the target service account's password
Domain SID

##### Step 1 — NTLM Hash
 
Since the plaintext password `Trustno1` for `svc_mssql` was already known, the NTLM hash was derived directly:
 
```terminal
python3 -c 'import hashlib; print(hashlib.new("md4", "Trustno1".encode("utf-16le")).hexdigest())'
```
 
This produces the NTLM hash used later when forging the ticket
 
OUTPUT 
```terminal
69596c7aa1e8daee17f8e78870e25a5c
```

##### Step 2 — Domain SID
 
While connected to the SQL Server as `svc_mssql`, the domain SID can be retrieved using a built-in T-SQL function
you could aswell grab it off bloodhound. But I wanted to make it a bit more complicated.


```terminal
SELECT SUSER_SID('BREACH\Domain Users');
```

Output given.

```
0x010500000000000515000000b98ceb8ab01277c5f09b182a01020000
```
 
This is a raw binary SID and must be parsed into the standard `S-1-5-21-...` format.
 
##### Parsing the binary SID
 
| Field | Bytes | Value |
|---|---|---|
| Revision | `01` | 1 |
| Sub-authority count | `05` | 5 |
| Identifier authority | `000000000005` | 5 (NT Authority) |
| Sub-authority 1 | `15000000` | 21 |
| Sub-authority 2 | `b98ceb8a` (little-endian) | 2330692793 |
| Sub-authority 3 | `b01277c5` (little-endian) | 3312915120 |
| Sub-authority 4 | `f09b182a` (little-endian) | 706255856 |
| Sub-authority 5 (RID) | `01020000` (little-endian) | 513 |
 
The final sub-authority 513 is the RID, not part of the domain SID. RID 513 corresponds to the Domain Users group, which is consistent with the query issued.
 
Dropping the RID leaves the domain SID:
 
```
S-1-5-21-2330692793-3312915120-706255856
```
